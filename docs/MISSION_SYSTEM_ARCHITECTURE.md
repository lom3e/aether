# Aether Mission System Architecture

## 1. Overview & Architectural Role

The **Mission System** represents the durable container for high-level user outcomes in Aether. A Mission is not a raw chat message; it is a structured, verifiable, multi-stage initiative that coordinates digital workforce specialists, tracks execution state, produces cryptographically hashed deliverables, and enforces automated quality gates.

The Mission System sits directly on top of the **Unified Execution Runtime**:

```text
User Request
    ↓
Personal Agent Orchestrator / API
    ↓
Mission & Milestone Stages
    ↓
Task (lineage: mission_id, parent_id, session_id, workspace_id)
    ↓
Unified Runtime (Runtime.execute)
    ↓
Specialist Execution (AgentTool / Workforce / Action / Tool)
    ↓
ExecutionResult
    ↓
Deliverable Harvesting (SHA-256) & Stage Output Persistence
    ↓
Quality Gate Evaluator (automated reviewer & rubric assertion)
    ↓
COMPLETED (or Rework / Awaiting Approval / Failed)
```

## 2. Core Domain Models

The mission domain models in `aether.missions.models` provide a strongly typed, backward-compatible representation:

### `Mission`
The root durable entity representing an outcome charter:
- `id`: Unique mission identifier (`msn-...`).
- `workspace_id`: Root workspace context.
- `title`: Outcome title.
- `objective`: Primary user goal or charter.
- `status`: Lifecycle state (`DRAFT`, `READY`, `PLANNING`, `RUNNING`, `WAITING`, `VERIFYING`, `AWAITING_APPROVAL`, `COMPLETED`, `FAILED`, `CANCELLED`, `BLOCKED`).
- `milestones`: List of `Milestone` (aliased as `MissionStep`).
- `plan`: Optional `MissionPlan` encapsulating ordered steps and dependencies.
- `progress`: Derived integer percent (`0` to `100`), calculated strictly as `int((completed_steps / total_steps) * 100)`.
- `current_stage`: Title of the actively executing step or stage.
- `deliverables`: List of registered `Deliverable` objects.
- `result`: Optional `MissionResult` summarizing final findings and verification status.

### `Milestone` / `MissionStep`
The individual verifiable stage within a mission:
- `id`: Milestone identifier.
- `mission_id`: Owning mission ID.
- `title`: Stage description.
- `description`: Detailed step instructions or constraints.
- `status`: Step lifecycle state (`PENDING`, `RUNNING`, `COMPLETED`, `FAILED`, `SKIPPED`, `WAITING`).
- `order_idx`: Sequence position.
- `assigned_agent`: Specific workforce agent responsible for this step (or `None` for coordinator dispatch).
- `execution_id`: Authoritative execution run ID.
- `output`: Result text or structured findings generated by runtime execution.
- `completed_at` / `started_at`: ISO-8601 timestamps.

### `Deliverable`
Verifiable artifact produced by milestone execution:
- `id`: Deliverable identifier (`del-...`).
- `mission_id`: Associated mission.
- `execution_id`: Associated execution run.
- `milestone_id`: Producing stage.
- `name`: File or artifact name.
- `path`: Absolute filesystem path within workspace.
- `type`: Category (`document`, `code`, `data`, `archive`).
- `size_bytes`: File size.
- `sha256`: SHA-256 cryptographic digest.
- `status`: Verification status (`verified`, `draft`, `needs_revision`, `final`).

## 3. Canonical Execution Pipeline

### Unified Runtime as the Single Execution Path
Milestones are executed via `workspace.runtime.execute(task)`. Rather than dispatching ad-hoc commands, the Mission Runtime builds a lineage-aware `Task`:

```python
task = Task(
    instruction=task_instruction,
    agent_name=target_agent or "unknown",
    workspace_id=ws_id,
    session_id=mission_id,
    mission_id=mission_id,
    parent_id=execution_id,
    mode=ExecutionMode.DELEGATE if not target_agent else None,
)
result = workspace.runtime.execute(task)
```

The Unified Runtime coordinates provider resolution, memory context injection, agent initialization, and `AgentTool` workforce delegation.

### Progress Derivation Invariant
Progress is never estimated using wall-clock timers or fake percentages.
Progress is derived deterministically from step resolution:
$$\text{progress} = \left\lfloor \frac{\text{completed steps}}{\text{total steps}} \times 100 \right\rfloor$$

### Terminal Completion Invariant
A mission **cannot** transition to `COMPLETED` before:
1. Every defined step has successfully resolved (`COMPLETED` or `SKIPPED`).
2. Automated Quality Gate verification passes.

If any stage fails, the mission transitions immediately to `FAILED` unless a rework cycle is permitted.

---

## 4. Quality Gate & Automated Verification

Following the completion of all stages, the mission transitions to `VERIFYING`. The `QualityGateEvaluator` (`reviewer.py`):
1. Analyzes produced deliverables and stage outputs against the mission objective.
2. Applies automated review rules (completeness, format integrity, substantive depth).
3. If passed (score $\ge 70$ and zero fatal redlines):
   - Deliverables are marked `verified`.
   - Deliverables and learnings are ingested into workspace memory.
   - Mission status transitions to `COMPLETED`.
4. If rejected:
   - Up to $N$ automated rework cycles are dispatched through `workspace.runtime.execute`.
   - If rework cycles are exhausted, human override approval is requested (`AWAITING_APPROVAL`).

---

## 5. Intent Tier Separation

The system strictly enforces conversational boundaries:
- **`ANSWER`**: Casual conversation, queries, and summaries execute via Runtime in-band without creating missions.
- **`DO`**: Safe local single-action file mutations execute via Runtime without creating missions.
- **`ACT`**: Safety-gated external mutations execute via Runtime without creating missions.
- **`DELEGATE`**: Deep investigation, multi-step analysis, and workforce coordination generate a durable `Mission` with milestones, executing asynchronously in background tasks.
