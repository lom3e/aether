# Aether v0.20.0 — Public API, DX & Architecture Review

Questo documento analizza formalmente lo stato dell'architettura di Aether post-v0.19.0 con un focus sulla *Developer Experience* (DX) e sulla prontezza per il rilascio v1.0. 

L'obiettivo strategico della v0.20.0 non è aggiungere funzionalità cognitive, ma stabilizzare il layer pubblico, definire l'Error Model, risolvere le ultime inefficienze sui dati strutturati e produrre una documentazione chiara.

---

## 1. Analisi dello Stato Attuale (Verificata)

### Public API
Attualmente, l'esportazione dei simboli nel framework è incostante e caotica per l'utente finale:
- **Corretto:** `aether.providers` e `aether.planning` esportano correttamente le astrazioni tramite i rispettivi `__init__.py`.
- **Assente:** `aether.core`, `aether.engine`, `aether.tools`, `aether.agents` hanno `__init__.py` quasi completamente vuoti.
- **Conseguenza:** Un'applicazione esterna è oggi costretta ad accoppiarsi al layout fisico dei file sorgente (es. `from aether.tools.base import Tool`), rendendo il codice fragile e in violazione del principio di astrazione.

### Structured Observation Safety
La milestone v0.19.0 ha garantito che l'Agent non trasformi prematuramente gli output in stringhe, passando `dict`, `list` e custom objects `DelegationResult` immutati alla `ObservationFactory`.
- **Problema residuo nel Budgeting:** `CharacterBudget.enforce()` calcola la lunghezza serializzando l'oggetto in JSON (o stringa). Se il JSON supera il limite, la classe taglia brutalmente la stringa e la restituisce. Questo causa **JSON invalidi/corrotti**, compromettendo gravemente la capacità del Planner di interpretare i dati se l'output era originariamente strutturato.

### Error Model
Il framework contiene eccezioni isolate (es. `ProviderError`, `RuntimeSafetyError`, `DelegationError`, `SkillLoadError`), ma manca un namespace unificato (`aether.errors`) che funga da gerarchia semantica. Uno sviluppatore non sa chiaramente quali eccezioni aspettarsi in fase di invocazione di `Agent.achieve()`.

### Packaging & Examples
- Il `pyproject.toml` è configurato come setup base per package discovery, ma non è esplicitamente preparato per un rilascio formale PyPI (metadati carenti, dipendenze deboli).
- Esiste solo un misero `examples/basic_agent/main.py`. Mancano del tutto flussi di lavoro dimostrativi reali (delegazione, Goal, runtime safety).

## 2. Obiettivi della v0.20.0

Questa milestone trasformerà Aether da "motore interno" a "libreria per sviluppatori".

### 1. API Pubblica Stabile & Facile (No internal imports)
L'utente deve poter importare tutte le primitive base in modo flat:
```python
from aether import Agent, Goal, Task
from aether.tools import Tool, CognitiveAgentTool
from aether.planning import Observation
from aether.providers import OllamaProvider
```
Implementeremo gli `__all__` in tutti gli `__init__.py` rilevanti, stabilendo un solido contratto di backward-compatibility verso il futuro.

### 2. Sicurezza dei Payload Strutturati (Observation Truncation)
Modificare il comportamento del budgeter: se il payload è strutturato e deve essere troncato, invece di generare un JSON invalido, si dovrà iniettare un metadato di allarme o generare un payload strutturato di fallback sicuro (es. ritornare un dizionario informativo del troncamento). La struttura deve sempre essere rispettata.

### 3. Unified Error Model
Introdurre `aether.errors` con eccezioni pubbliche chiare (distinguendo tra System, Provider, Execution, Planning). In questo modo, l'app chiamante può far reagire la propria UI o la propria business logic ai fallback.

### 4. Examples & DX
Fornire 6 script python indipendenti e funzionanti che testano la Public API coprendo Agent Base, Provider Locali, Tool, Goal-driven agents e Delegation.

### 5. Packaging & v1.0 Readiness
Revisione del `README.md`, completamento del `pyproject.toml`, per raggiungere uno stato di *distribuibilità*.

---

## 3. Cosa NON entrerà nella v0.20.0
Si ribadisce che la v0.20.0 è esclusivamente una milestone di consolidamento della UX dello sviluppatore. Non si accetteranno:
- Feature cloud-native / distribuite.
- Euristiche aggiuntive del Planner (che appesantirebbero i prompt).
- Memoria globale multi-agente.
- Vector store complessi come layer obbligatori.

La prossima mossa è sviluppare il codice seguendo fedelmente l'Implementation Plan.
