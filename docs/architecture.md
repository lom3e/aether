# Aether v1.0 Architecture

This document describes the official architecture of Aether v1.0.0.

Aether is built around a robust, decoupled architecture separating cognitive reasoning (the Planner) from runtime mechanics (the Execution Engine). This separation ensures that agents can safely operate in loops, handle failures resiliently, and propagate structured data without corrupting JSON payloads.

---

## 1. High-Level Overview

The Aether framework relies on a primary cognitive loop coordinated by the `Agent`. The loop follows a **Plan → Execute → Observe → Decide** pattern.

### The Cognitive Loop

```mermaid
flowchart TD
    A[Agent] -->|achieve(goal)| B(Planner)

    subgraph Cognitive Layer
    B -->|Generates| C[CognitivePlan]
    C --> D[PlanCompiler]
    end

    subgraph Execution Layer
    D -->|Translates to| E[ExecutionPlan]
    E --> F[ExecutionEngine]
    F -->|Dispatches| G[Tool / Skill]
    G -->|Returns| H[ExecutionResult]
    end

    subgraph Observation Layer
    H --> I[ObservationFactory]
    I -->|Transforms to| J[Observation]
    end

    J -->|Feedback to| B
    B -->|Evaluates| K[PlanValidator]
    K -->|Produces| L{Decision}

    L -->|FINISH| M[Agent returns Result]
    L -->|CONTINUE| B
    L -->|FAIL| M
```

## 2. Component Boundaries

Aether strictly enforces the following architectural boundaries.

### 2.1 The Agent (Orchestrator)
**Class**: `aether.Agent`

The `Agent` is the core orchestrator. It manages the agent's identity, memory, tool registries, and the runtime safety policy.
- **What it does**: Initializes the cognitive loop (`achieve()`), manages the `ExecutionContext`, and bridges the Cognitive Layer with the Execution Layer.
- **What it does NOT do**: The `Agent` contains **no** provider-specific logic, **no** cognitive heuristics (delegated to Planner), and **no** tool dispatch logic (delegated to ExecutionEngine).

### 2.2 The Cognitive Layer
**Classes**: `BasePlanner`, `BasicPlanner`, `CognitivePlan`, `PlanCompiler`, `PlanValidator`, `Decision`

This layer is responsible for interacting with the AI provider, formulating strategies, and evaluating outcomes.
- **Planner**: Generates a `CognitivePlan` (reasoning, thoughts, and proposed tools).
- **PlanCompiler**: Translates the string/JSON representations of a `CognitivePlan` into an actionable `ExecutionPlan`.
- **PlanValidator**: Analyzes observations against the active goal to produce a formal `Decision` (`FINISH`, `CONTINUE`, or `FAIL`).

### 2.3 The Execution Layer
**Classes**: `ExecutionEngine`, `ExecutionPlan`, `Task`, `ToolCall`, `ExecutionResult`

The runtime mechanics of Aether.
- **ExecutionEngine**: Wholly independent from the Planner. It receives an `ExecutionPlan` and dynamically dispatches actions (Tools or Skills) via internal executors.
- **Independence**: The ExecutionEngine operates blindly to cognitive goals; it only knows how to execute a unit of work and return an `ExecutionResult`.

### 2.4 The Observation Layer
**Classes**: `ObservationFactory`, `Observation`, `CharacterBudget`

The translation layer between the raw output of execution and the intelligence layer.
- **ObservationFactory**: Purely technical. It transforms an `ExecutionResult` into a structured `Observation`.
- **Structured Data Safety**: Preserves structural types (`dict`, `list`) when generated by tools. When budget enforcement truncation occurs, structured objects are never forcibly cast to string (which would corrupt JSON), but instead fall back to safe dictionary representations.

### 2.5 The Provider Layer
**Classes**: `AIProvider`, `OllamaProvider`, `MockProvider`, `ResilientProvider`, `ProviderConfig`, `Message`, `ProviderResponse`

An abstract layer normalizing communication with LLM backends.
- **Provider Abstraction**: Aether components talk to `AIProvider` using standard `Message` objects.
- **ResilientProvider**: A composable decorator that wraps any `AIProvider` to add automatic retry logic with exponential backoff for transient failures (e.g., rate limits, connection drops).

## 3. Runtime Safety

Aether is designed for autonomous operation, making infinite loop protection a critical infrastructural requirement.

**Classes**: `RuntimeSafetyPolicy`, `Deadline`

- **RuntimeSafetyPolicy**: Enforces hard infrastructural constraints on the execution loop:
  - `max_cognitive_cycles`: Maximum turns allowed.
  - `max_replans`: Maximum continuous failures/replans.
  - `deadline`: An absolute timeout constraint.
- **Infrastructural Purity**: The safety policy operates objectively. It uses counters and timestamps without attempting to evaluate cognitive progress.

---

## 4. Agent Delegation

Aether supports multi-agent coordination natively without introducing heavy new architectural concepts like "swarms".

**Class**: `CognitiveAgentTool`

- **Delegation as a Tool**: Child agents are wrapped inside a `CognitiveAgentTool`. To the parent agent, the child is simply a tool it can call.
- **Contracts**: Uses `DelegationRequest` and `DelegationResult`.
- **Isolation**: Each agent maintains its own `AgentContext`, `MemoryManager`, and runtime state. The parent passes instructions downward, and the child returns an outcome upward, keeping architectures fully uncoupled.

---

## 5. Error Boundaries

Aether provides a unified semantic error model designed for consumption by developers. All framework errors inherit from `AetherError`.

- `AetherError` (Base)
  - `PlanningError`: Cognitive layer failures (e.g., invalid JSON from LLM).
  - `ExecutionError`: Tool execution or dispatch failures.
    - `DelegationError`: Failures specific to inter-agent delegation.
  - `ProviderError`: LLM endpoint failures (`AuthenticationError`, `RateLimitError`, `ProviderConnectionError`).
  - `RuntimeSafetyError`: Thrown when the `RuntimeSafetyPolicy` constraints are exceeded.
  - `AetherFatalError`: Unrecoverable internal framework faults.

System-level exceptions like `KeyboardInterrupt` or `SystemExit` bypass `AetherError` completely to ensure standard Python process management works as expected.
